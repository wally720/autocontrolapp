Documentación Técnica: Auto Gasto PRO

Guía integral de arquitectura, desarrollo y mantenimiento del sistema.

1. Contexto y Definición del Proyecto

¿Qué es Auto Gasto PRO?

Auto Gasto PRO es una solución digital moderna desarrollada como una Aplicación Web Progresiva (SPA). Su propósito central es digitalizar la gestión financiera y operativa de vehículos automotores. A diferencia de las hojas de cálculo tradicionales o libretas físicas, esta aplicación ofrece una interfaz centralizada, accesible desde cualquier dispositivo móvil o de escritorio, garantizando que la información esté siempre sincronizada en la nube.

Propósito y Objetivos Estratégicos

El desarrollo de esta herramienta responde a la necesidad de control financiero sobre los activos vehiculares. Sus objetivos principales son:

  • Centralización de Datos: Eliminar la dispersión de información agrupando costos de combustible, mantenimientos, impuestos y seguros en una única base de datos.
  • Análisis de Rendimiento: Permitir al usuario calcular métricas clave como el consumo de combustible (Galones/Km) mediante la captura obligatoria de odómetros en las cargas de gasolina.
  • Mantenimiento Preventivo: Facilitar la toma de decisiones sobre cuándo realizar servicios basándose en el historial de gastos y fechas.
  • Accesibilidad Universal: Proveer acceso seguro e inmediato a la información histórica, crucial en momentos de venta del vehículo o reclamaciones de garantía.

Alcance Funcional

El sistema está diseñado para cubrir el ciclo de vida operativo del vehículo en manos del usuario:

  1. Gestión de Identidad: Sistema robusto de autenticación delegada (OAuth con Google) para evitar la gestión manual de contraseñas y aumentar la seguridad.
  2. Administración Multi-vehículo: Capacidad escalable para que un solo usuario gestione desde un vehículo personal hasta una pequeña flota familiar o empresarial, con conmutación instantánea de contextos de datos.
  3. Registro Detallado de Transacciones: Módulo de captura de datos con validaciones específicas por tipo de gasto (ej. validación de odómetro secuencial lógica).
  4. Reportaría Histórica: Visualización cronológica y filtrada de gastos para auditoría rápida.

2. Arquitectura de Software

La aplicación adopta una arquitectura Serverless (Sin Servidor) y Event-Driven (Basada en Eventos) en el cliente, aprovechando el ecosistema de Firebase. Esto elimina la necesidad de administrar servidores backend tradicionales, permitiendo un escalado automático y reducción de costos operativos.

Estructura del Proyecto (Exploración de Carpetas)

El código fuente en src/ está organizado modularmente para facilitar la mantenibilidad:

  • config/: Centraliza la inicialización de servicios externos. Aquí reside firebase.js, que actúa como singleton para las instancias de auth y firestore.
  • context/: Implementa el patrón "Provider" de React.
    • AuthContext: Mantiene la sesión del usuario y escucha cambios en el estado de autenticación (`onAuthStateChanged`).
    • VehicleContext: Gestiona qué vehículo está "activo". Esto es crítico porque toda la aplicación filtra los datos basándose en este contexto.
  • features/: Contiene componentes que encapsulan lógica de negocio compleja.
    • ExpenseForm: No es solo una vista, contiene la lógica de validación de formularios y construcción del objeto de gasto.
    • ExpenseHistory: Maneja la presentación de listas.
  • hooks/: Custom Hooks que abstraen la conexión a la base de datos. Ejemplo: useExpenses encapsula la suscripción en tiempo real a Firestore, separando la capa de datos de la capa de vista.

4. Lógica de Aplicación y Modelo de Datos

Nota Importante: Esta sección describe cómo reconstruir la lógica del sistema desde cero, detallando las reglas invisibles que gobiernan el comportamiento de la aplicación.

4.1 Modelo de Datos (Esquema NoSQL)

Colección: users

Representa la entidad del cliente. Se crea automáticamente la primera vez que un usuario inicia sesión.

{
  "id": "String (UID provisto por Firebase Auth)",
  "email": "String (Email de Google)",
  "role": "String ('user' por defecto, escalable a 'admin')",
  "status": "String ('active' | 'pending')",

  // ARRAY CRÍTICO:
  // Contiene los identificadores (Placas o IDs) de los vehículos que el usuario puede ver.
  // Esta desnormalización permite evitar lecturas extra a una colección de permisos.
  "vehicles": [
    "ABC-123",
    "XYZ-987"
  ],

  "createdAt": "ISO 8601 String"
}

Colección: expenses

Almacena los eventos transaccionales. Esta colección puede crecer indefinidamente.

{
  "id": "String (Auto-ID de Firestore)",

  // CLAVES FORÁNEAS LÓGICAS (Indexadas):
  "vehicleId": "String (Debe coincidir con uno del array 'vehicles' del usuario)",
  "userId": "String (UID del creador del registro)",

  // DATOS TRANSACCIONALES:
  "date": "String (Formato YYYY-MM-DD para ordenamiento simple)",
  "category": "String (Combustible, Mantenimiento, Seguros, etc.)",
  "amount": "Number (Monto monetario, sin divisa específica)",
  "notes": "String (Texto libre opcional)",

  // DATOS CONDICIONALES (Solo si category === 'Combustible'):
  "odometer": "Number (Kilometraje al momento de la carga)",
  "gallons": "Number (Cantidad de combustible)"
}

4.2 Reglas de Negocio y Validaciones

Flujo de Creación de Gastos

  1. Verificación de Contexto: El sistema primero verifica si existe un selectedVehicle en el estado global. Si el usuario no tiene vehículos asignados, el formulario se bloquea o no se procesa.
  2. Validación de Integridad:
    • El campo amount debe ser numérico y mayor a 0.
    • La date no puede ser vacía (por defecto es "hoy").
  3. Lógica Condicional de Combustible:
    • Si el usuario selecciona "Combustible", el sistema despliega campos adicionales (odometer, gallons).
    • Estos campos se vuelven obligatorios bajo esta condición para asegurar la calidad de los datos de reportes futuros.

Gestión de Estado del Vehículo

El VehicleContext maneja una lógica inteligente de selección:

  • Al cargar la app, lee el array vehicles del perfil de usuario.
  • Si el usuario tiene vehículos pero no ha seleccionado ninguno (estado inicial), el sistema selecciona automáticamente el primero de la lista (vehicles[0]).
  • Esto asegura que el usuario nunca vea una pantalla vacía "sin datos" si ya tiene información registrada.

4.3 Estrategia de Consultas (Queries)

La aplicación optimiza los costos de lectura de Firestore utilizando índices compuestos implícitos.

Query Principal (Historial de Gastos):

// Pseudo-código SQL equivalente
SELECT * FROM expenses
WHERE vehicleId = 'VEHICULO_SELECCIONADO'
ORDER BY date DESC;

Esta query asegura que:

  1. Nunca se descarguen datos de otros vehículos (Seguridad y Rendimiento).
  2. Los datos siempre lleguen ordenados cronológicamente inverso (lo más nuevo arriba).

4.4 Reglas de Seguridad (Seguridad en la Nube)

Dado que es una app Serverless, la seguridad no está en el servidor de aplicaciones, sino en la base de datos misma. Las reglas inferidas para proteger este esquema son:

// Reglas lógicas para Firestore
service cloud.firestore {
  match /databases/{database}/documents {

    // Regla 1: Integridad de Usuario
    // Un usuario solo puede leer/escribir su propio documento de perfil.
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }

    // Regla 2: Aislamiento de Gastos
    // Un usuario solo puede crear gastos si se asigna a sí mismo como propietario (userId).
    // Un usuario solo puede leer/modificar gastos donde él sea el propietario (userId).
    match /expenses/{expenseId} {
      allow create: if request.auth != null && request.resource.data.userId == request.auth.uid;
      allow read, update, delete: if request.auth != null && resource.data.userId == request.auth.uid;
    }
  }
}
